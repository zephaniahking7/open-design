PART TWO — LEAD NOTIFICATION SYSTEM

Current state: when a brief or lead is submitted, data lands 
in Postgres but no notification fires. Operator must manually 
check /studio.

Target: real-time email notification on every brief submission 
AND every lead submission, sent to the operator's email.

Discovery first (do not implement until confirmed):
- Inspect .local/skills/ for any email skill (Replit's built-in 
  email integration, Resend, SendGrid, or other)
- If a skill exists, identify what secrets it requires
- If no skill exists, recommend the simplest available option 
  and identify required secrets
- Report findings in plan output before any implementation

Once email provider is confirmed, the notification logic should:
- Fire asynchronously after successful insert into bonanza_briefs 
  OR bonanza_leads (non-blocking — submission must succeed 
  even if email fails)
- Use sparse, on-brand templates:

For briefs:
Subject: New brief — {client_name}
Body: "A brief just arrived in the studio.

From: {client_name} <{client_email}>
Vision: {first 200 chars of vision}
Budget: {budget_note or 'Not specified'}

Triage at: {studio_url}

— Bonanza Cr8tives"

For renders (lead capture):
Subject: New render captured — {email}
Body: "A render was captured.

From: {email}
Vision: {first 200 chars of vision}
AI output: {first 200 chars of ai_output}

Triage at: {studio_url}

— Bonanza Cr8tives"

- Operator email address: requested via secrets skill 
  (BONANZA_OPERATOR_EMAIL). Do not hardcode.
- Failure mode: if email send fails, log to console + insert 
  a row into bonanza_notifications table with status 'failed'. 
  Do not surface error to public submitter.
- Rate limit on notification sends: max 30 per hour to prevent 
  spam loops if rate limiting is bypassed somewhere upstream.

Schema for notification log:
CREATE TABLE bonanza_notifications (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  type        text NOT NULL CHECK (type IN ('brief', 'lead')),
  source_id   uuid NOT NULL,
  recipient   text NOT NULL,
  status      text NOT NULL CHECK (status IN ('sent', 'failed', 'deferred')),
  error       text,
  created_at  timestamptz DEFAULT now()
);
CREATE INDEX bonanza_notifications_created_at_idx ON bonanza_notifications (created_at DESC);

PART FOUR — ERROR TRACKING

Current state: errors that occur in production (failed API 
calls, render failures, brief submission errors) leave no 
trace beyond browser console.

Target: lightweight server-side error logging to Postgres. 
No third-party service. Operator can see errors via /studio 
in a future pass.

Schema:
CREATE TABLE bonanza_errors (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  source      text NOT NULL,
  message     text NOT NULL,
  stack       text,
  context     jsonb,
  user_agent  text,
  url         text,
  created_at  timestamptz DEFAULT now()
);
CREATE INDEX bonanza_errors_created_at_idx ON bonanza_errors (created_at DESC);

Implementation:
- New endpoint POST /api/error (rate limited at 20 per IP per 
  hour to prevent flood attacks)
- Frontend: place window.addEventListener('error', ...) and 
  window.addEventListener('unhandledrejection', ...) at the 
  app root if safe, but ensure they do not increase public 
  landing bundle unnecessarily. Listeners POST to /api/error 
  on capture.
- Backend: wrap /api/render, /api/leads, /api/brief, and all 
  /api/studio/* handlers with a try/catch that inserts to 
  bonanza_errors on uncaught exceptions
- Do not expose stack traces in HTTP responses to clients — 
  return generic error message, log full detail server-side
- Add a simple GET /api/studio/errors endpoint (X-Bonanza-Internal 
  header gated) that returns the latest 100 errors for future 
  studio integration. Do not build the studio UI for it in 
  this pass — just the endpoint and schema.
